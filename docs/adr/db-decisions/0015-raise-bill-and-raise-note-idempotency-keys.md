# Raise Bill and Raise Note carry a client idempotency key on the paper they write

A double submit of Raise Bill or Raise Note (a double tap, a retry after a dropped response) must not write a second Bill or Note, burn a second MB / MC / MD number or post the Ledger twice. Checkout already solves this with a unique `orders.idempotency_key` (Spec F), but an office Bill has no order and a Note has nothing above it. So `bills` and `notes` each gain a nullable `idempotency_key` varchar(128), unique (`bills_idempotency_key_unique`, `notes_idempotency_key_unique`). Postgres allows many NULLs under a unique constraint, so every Bill written by checkout and every Note written by Correct and Cancel keeps it null; only Raise Bill and Raise Note set it. A checkout Bill's key stays on its order.

The client sends one key per Raise form, kept across retries and rotated only after a success (up to 120 characters, the same schema as checkout). The key is looked up first: if a Bill (or Note) already has it and the call names the same Customer and the same Variety quantities (or the same Bill, kind and line quantities), the first result is returned and nothing is written. If the payload differs, the call is refused `idempotency_key_reused`. Two attempts racing with one key both run; the loser's insert hits the unique constraint, its whole transaction rolls back (including the number it allocated, which is gapless and in the same transaction), and it returns the winner's result. The payload is compared against what the paper already stores (the first Bill version's items, the Note's lines), so no request hash is kept, and a replay after a later Correct still returns the first Raise Bill result. A replayed balance is rebuilt from the Ledger by `occurredAt`, so it can differ from the first answer after a back-dated Opening balance (the same as Spec F). Correct and Cancel are not keyed; `expectedVersionNumber` and the cancelled marker already guard them. Migration `0004_raise_idempotency_keys`.

**Considered:** one `idempotency_keys` table (key, kind, paper id, request hash) shared by both actions: more general, but a second table to write in every transaction and a hash that duplicates what the paper already says, for two call sites. A key derived from the payload instead of sent by the client: it cannot tell a deliberate second identical Note from a double tap. Client-only button disabling: does not survive a retry after a lost response.
