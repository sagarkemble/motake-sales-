# The WhatsApp access token lives in Supabase Vault; a token change is an audit row, not a table

Spec J-0 (#66) gives the WhatsApp access token two sources of truth: the master copy in Supabase Vault (the `supabase_vault` extension, schema `vault`) and a working copy in a secret file on the notification server. No application table is added. The master copy is one Vault secret found by a fixed name (env `WHATSAPP_TOKEN_VAULT_SECRET_NAME`, default `motake_whatsapp_access_token`), written with `vault.create_secret` / `vault.update_secret` and read from `vault.decrypted_secrets` over the normal database connection, so no extra Supabase key is needed. Only server code touches it. The secret's `description` holds `{"updatedBy": "<profile id>"}` of the Admin who last saved it and Vault's own `updated_at` says when, so the settings screen shows last 4 characters, updated at and updated by with nothing else stored.

Saving a token writes one `audit_logs` row: `action = token_updated`, `entity_type = whatsapp_token`, `entity_id` = the Vault secret's id, payload `{ last4 }` only. The token itself never goes in the audit row, a log line, an error or an API response. Both enum values are new (db-decisions/0012): no existing entity type names the token, and `entity_id` must be a uuid, which the Vault secret id is. Migration `0005_whatsapp_token_audit`. A "held" message is not a new status either: it is a `pending` notification whose current run's latest attempt failed as `auth_error`.

**Considered:** a `whatsapp_token_settings` table for updated by / updated at (a second place that can drift from Vault, for two display fields); deriving updated by and updated at from the audit log (a token seeded or changed by hand in Vault would show a stale time); keeping the token in the env file (the problem Spec J-0 fixes); a Supabase API key for Vault (one more secret for what SQL already does).
